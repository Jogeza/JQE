# External repository audit and recommendations for JQE — 2026-10-08

Recommendation: use QuantDinger as an engineering reference and Institutional-Quant-Engine as a teaching catalogue. Adopt neither as JQE's trading engine. JQE's immediate priorities are verifiable data, realistic account-currency research, reproducible experiment identities and controlled out-of-sample evaluation. More algorithms, AI agents, infrastructure or Rust do not establish an edge.

This is an audit and recommendations only. Qoder is concurrently working on JQE. No JQE source, strategy, execution, environment file, dataset, terminal, persisted safety state or running service was changed for this audit. No dependencies were installed, external project code imported/executed, tests run or trading/backtest jobs started. Separate source snapshots were downloaded under Git-ignored `reports/repository-audit-20261008/`; static parsing of educational Python files did not execute them. The only deliverable added to JQE is this document.

## Repository 1: Institutional-Quant-Engine

The README presents a broad quantitative-finance curriculum and also identifies educational use. Its module names are useful pointers to subjects, but the sampled implementations do not establish an integrated institutional trading platform. [README at inspected commit](https://github.com/Rakeshks7/Institutional-Quant-Engine/blob/aef5608c41014827d8acd5d47682b9981f8dc753/README.md).

| Finding | Evidence and implication for JQE |
| --- | --- |
| Event-driven backtester has defective accounting | On each ORDER, the example assigns holdings to 100 rather than accumulating them, while subtracting 10,500 from cash again. Repeated signals therefore do not produce a consistent cash/holdings ledger. It also lacks a demonstrated fill/fee/exit model. Keep JQE's canonical engine; do not transplant this one. [Code, lines 27–54](https://github.com/Rakeshks7/Institutional-Quant-Engine/blob/aef5608c41014827d8acd5d47682b9981f8dc753/infrastructure_core/18_event_driven_backtester.py#L27) |
| HMM example is retrospective, not validated prediction | It fits and predicts on the same generated sequence. This can illustrate regimes but cannot establish causal out-of-sample identification or an entry edge. The file also starts with notebook `!pip` syntax and does not parse as an ordinary Python module. [HMM example](https://github.com/Rakeshks7/Institutional-Quant-Engine/blob/aef5608c41014827d8acd5d47682b9981f8dc753/ai_deep_learning/31_regime_detection_hmm.py#L1) |
| “EVT-adjusted CVaR” is not supported by the calculation | The code fits a generalized Pareto distribution but reports the empirical mean of selected absolute tail losses; fitted parameters are not used to calculate that output. A variable named `var_99` is assigned the fifth-percentile threshold. This is inadequate validation of a 99% tail-risk estimate. [EVT example, lines 11–23](https://github.com/Rakeshks7/Institutional-Quant-Engine/blob/aef5608c41014827d8acd5d47682b9981f8dc753/risk_portfolio/24_tail_risk_evt.py#L11) |
| Classification accuracy is not a trading result | The XGBoost demonstration does use a chronological 80/20 split, which is a useful starting pattern. However, `np.where(next_return > 0, 1, 0)` assigns the final unknown next return to class 0; the subsequent `dropna()` cannot remove that fabricated target. Accuracy is reported without an execution/cost/expectancy comparison. [Predictor](https://github.com/Rakeshks7/Institutional-Quant-Engine/blob/aef5608c41014827d8acd5d47682b9981f8dc753/strategies/11_ml_xgboost_predictor.py#L17) |
| Baseline backtest is a simplified historical illustration | Its lagged SMA signal avoids directly multiplying today's decision by today's return. But positions are 0/1, not a complete long/short execution simulation, and the script lacks realistic costs, a frozen dataset manifest and a selection-controlled holdout. [Trend example](https://github.com/Rakeshks7/Institutional-Quant-Engine/blob/aef5608c41014827d8acd5d47682b9981f8dc753/strategies/01_trend_following_backtest.py) |
| Reproducibility and packaging are weak | Static parsing found syntax failures in `31_regime_detection_hmm.py` and `02_live_paper_trader.py`. Requirements have no version pins. The covariance example imports seaborn, absent from those requirements. Several examples perform work at module scope. There is no discovered automated test suite/CI at this snapshot. [Requirements](https://github.com/Rakeshks7/Institutional-Quant-Engine/blob/aef5608c41014827d8acd5d47682b9981f8dc753/requirements.txt), [covariance example](https://github.com/Rakeshks7/Institutional-Quant-Engine/blob/aef5608c41014827d8acd5d47682b9981f8dc753/risk_portfolio/25_covariance_shrinkage.py) |

Useful ideas to study later: covariance shrinkage for correlated exposure; causal state estimation for regime hypotheses; tail-risk measurement; performance profiling before optimization. Reimplement a small, specified hypothesis with independent tests and the canonical pipeline if evidence justifies it. The Ray example largely parallelizes artificial sleeps, so it does not benchmark JQE or establish a need for distributed infrastructure. [Ray example](https://github.com/Rakeshks7/Institutional-Quant-Engine/blob/aef5608c41014827d8acd5d47682b9981f8dc753/infrastructure_core/53_distributed_grid_ray.py).

Do not borrow its generated prices as Weltrade evidence. OFI/queue models require appropriate order-book observations; OHLC tick volume cannot establish them. News/fundamental, exchange-routing, options-pricing and tax modules largely address different instruments and market structures. Kelly sizing with assumed positive drift is especially inappropriate as a response to JQE's unproven expectancy.

The README says MIT, but no standalone root LICENSE was found in the inspected tracked tree. Clarify the project's licence artefacts before copying source. This audit copies no external implementation.

## Repository 2: QuantDinger

QuantDinger provides substantially more concrete engineering material: separate simulated execution, explicit data-clock phases, structured records, regression tests and CI checks. Those are useful design references. Their existence does not establish successful operation of every advertised broker, secure hosting, or positive out-of-sample expectancy for JQE.

| Worth learning from | Concrete evidence | JQE application |
| --- | --- | --- |
| Explicit bar-phase ordering | Tests distinguish opening callbacks, intrabar protection, closing callbacks and next-bar orders. [Phase-ordering tests](https://github.com/OpenByteInc/QuantDinger/blob/ba8cd667acca3e934bbc1cb354922eff413393dc/backend_api_python/tests/test_strategy_v2_bar_phase_ordering.py) | Specify and test JQE's existing closed-bar → next-open sequence, including a stop on the entry bar and no retroactive re-entry |
| Execution evidence separated from request/reference price | Tests reject missing execution prices and prohibit using limit/request prices as fills. [Price-evidence tests](https://github.com/OpenByteInc/QuantDinger/blob/ba8cd667acca3e934bbc1cb354922eff413393dc/backend_api_python/tests/test_execution_price_evidence.py) | Preserve the distinction between signal price, simulated fill, broker-reported fill and unresolved outcome in research/journal displays |
| Failure-oriented release tests | A fake adapter exercises partial fill, cancel/fallback, closing and restart idempotency. [Release gate](https://github.com/OpenByteInc/QuantDinger/blob/ba8cd667acca3e934bbc1cb354922eff413393dc/backend_api_python/tests/release_gate/test_live_execution_release_gate.py) | Map relevant scenarios to existing JQE fake-gateway tests; retain current fail-closed recovery and duplicate controls. This is a future test recommendation, not permission to change execution |
| Time-indexed equity and structured ledgers | The V2 runtime records equity, holdings, order events, executions and reconciliation results. [Runtime](https://github.com/OpenByteInc/QuantDinger/blob/ba8cd667acca3e934bbc1cb354922eff413393dc/backend_api_python/app/services/strategy_v2/runtime.py#L1752) | Add research-only marked-to-market evidence to canonical reports, with reconciliation to cash and closed trades |
| Metric contract tests | Information-ratio tests align return periods and reject missing continuous-market periods. [Metric tests](https://github.com/OpenByteInc/QuantDinger/blob/ba8cd667acca3e934bbc1cb354922eff413393dc/backend_api_python/tests/test_backtest_metrics.py) | Make frequency, gap policy, observations and undefined statuses explicit; avoid annualizing irregular trade returns as daily observations |
| Point-in-time factor evaluation | The factor-research engine carries membership, forward outcomes, turnover and costs. [Factor engine](https://github.com/OpenByteInc/QuantDinger/blob/ba8cd667acca3e934bbc1cb354922eff413393dc/backend_api_python/app/services/strategy_v2/factor_research.py) | Use the evidence structure for feature diagnostics; its cross-sectional stock factors are not automatically relevant to Weltrade synthetic contracts |
| Layered CI | Workflow source includes syntax/lint/structure/lock checks, split backend tests, accounting integration tests and release gates. [Backend CI](https://github.com/OpenByteInc/QuantDinger/blob/ba8cd667acca3e934bbc1cb354922eff413393dc/.github/workflows/basic-ci.yml) | Extend JQE's existing Windows backend and frontend CI selectively; avoid replacing it with a new stack |
| Security-specific checks and isolated code workers | Security workflow includes dependency/source/secret scans; user-code workers use a clean environment and JSON transport. [Security CI](https://github.com/OpenByteInc/QuantDinger/blob/ba8cd667acca3e934bbc1cb354922eff413393dc/.github/workflows/security-ci.yml), [worker](https://github.com/OpenByteInc/QuantDinger/blob/ba8cd667acca3e934bbc1cb354922eff413393dc/backend_api_python/app/utils/safe_exec_worker.py) | Add supply-chain checks when authorized. Keep generated code outside broker authority; JQE currently does not need arbitrary strategy-code execution |

Important limitations and findings:

1. **Profit-factor edge case is misleading.** The V2 result calculation returns gross profit itself when there are profits and no losses. That is a cash magnitude rather than a dimensionless ratio; changing account scale would change “profit factor.” JQE already has explicit profit-factor status fields: preserve that stronger contract rather than copying this fallback. [Result calculation](https://github.com/OpenByteInc/QuantDinger/blob/ba8cd667acca3e934bbc1cb354922eff413393dc/backend_api_python/app/services/strategy_v2/runtime.py#L2032).
2. **Generic costs cannot be transferred to Weltrade.** Default commission/slippage rates are each 0.0005. They are assumptions, not JQE's observed spread, MT5 lot economics, commission or funding. Instrument-rule snapshots are a useful pattern, but require terminal-verified JQE inputs. [Cost normalization](https://github.com/OpenByteInc/QuantDinger/blob/ba8cd667acca3e934bbc1cb354922eff413393dc/backend_api_python/app/services/backtest_execution.py).
3. **The sampled research engine is not a complete promotion protocol.** No walk-forward/purge/embargo/holdout/deflated-Sharpe implementation was found by those searches in the inspected V2 and backtest service directories. That is a bounded search result, not a claim that the entire repository has none. Its factor diagnostics do not replace JQE's chronological, selection-controlled canonical evaluation.
4. **Code filtering is not proof of hostile-code containment.** The isolated helper is useful, but the generic `safe_exec_isolated` path documents Linux-only memory limits, while manifest discovery has a separate Windows resource path. V2 callbacks are directly invoked by the runner; outer process isolation must be assessed separately. This audit demonstrates no exploit and certifies no sandbox. Do not introduce a user-code executor onto JQE's MT5 workstation on the strength of allowlists. [Execution helper](https://github.com/OpenByteInc/QuantDinger/blob/ba8cd667acca3e934bbc1cb354922eff413393dc/backend_api_python/app/utils/safe_exec.py#L760).

Root LICENSE is Apache-2.0 at this snapshot. No dependency-by-dependency licence audit was performed. Broad crypto/equity adapters, SaaS billing, agents, PostgreSQL/Redis and distributed workers are not requirements for JQE's current single-workstation, Weltrade-only scope.

## JQE: preserve strengths and address actual gaps

JQE already has clean broker boundaries, a canonical strategy bridge, immutable dataset hashing, chronological splits, holdout locking, experiment records, CPCV/PBO/DSR-related modules, quote-replay research, fail-closed execution controls, offline tests and CI. These should be connected and verified, not duplicated because another repository has more feature names. The existence of a statistical module does not show it is correctly integrated into every research campaign.

The earlier [entry-quality audit](2026-10-08-entry-quality.md) found 33 baseline test trades averaging −0.367 R at illustrative costs, nine provenance exclusions, and no verified account-currency expectancy. Those are historical results for its recorded strategy/configuration, not a fresh assessment of Qoder's current work.

Current uncommitted diffs include direction-relative momentum, normal-volatility scoring changes, the canonical regime re-export and a common spread fallback. They appear to address some earlier diagnostic issues, but this audit neither changes nor verifies their outcomes. Do not repeat the old “SELL unreachable” finding as a current verified defect. The six-factor total is still recorded separately from the operative raw-signal confidence in the inspected StrategyEngine; whether that should change requires a separately frozen hypothesis, not an automatic confidence-model replacement.

Insufficient evidence produces “needs more data”; failure produces “reject.” Neither outcome authorizes new live orders.

## What this audit does not establish

Neither repository has been demonstrated here to improve JQE's expectancy, solve its data gaps, or qualify it as institutional. No strategy was imported, tuned, backtested, adopted or deployed. No external test suite was executed; file counts and CI definitions are not test-pass claims. Current Qoder changes remain unverified by this audit. The prior test totals and prior baseline outcomes must not be presented as fresh validation of concurrent modifications.

The practical next task, once Qoder's work is finished, is a pinned canonical baseline and a review of data/economics qualification. Engineering quality can be improved incrementally; an entry edge must still be demonstrated on untouched, cost-aware chronological evidence.
